# Supported C++ Feature Matrix

`cppbolt` implements a defined, correctness-oriented subset of C++17. Every supported feature is covered by automated corpus tests and pinned by cryptographic golden hashes. Features outside the subset are either explicitly rejected with clear diagnostics or tracked as planned future extensions.

The baseline test status is tracked in `tests/PASSING.txt`. Run the test runner to verify status locally:

```sh
cargo run --bin cppbolt-testrunner -- target/release/cppbolt-cli
```

## Known Limitations & Design Rules

### SFINAE Audit (2026-11-19): Supported Subset and Remaining Gaps
The six SFINAE milestones (typed substitution failure, dependent nested types, instantiation rollback, expression SFINAE, partial-specialization/pack SFINAE, standard traits) are implemented. The following cases remain outside that subset and are **not** accepted the way Clang/GCC accept them:

- `decltype(auto)` return types (`template<class T> decltype(auto) f(T&&)`) are not parsed; use an explicit trailing return type instead.
- C-style ellipsis parameters (`int f(T, ...)`) are not modeled in function signatures, so such an overload cannot accept extra call arguments and cannot serve as a fallback. Use a typed parameter or a parameter pack for the fallback overload.
- Bit-fields (`struct S { int x : 3; };`) are not part of the type/parser model, so `decltype(s.x)` on a bit-field cannot be expressed.
- Wide character types (`wchar_t`, `char16_t`, `char32_t`) have no distinct type representation. They parse as opaque names: `std::is_integral<char16_t>::value` yields `false` and `sizeof(char16_t)` is 4 rather than 2.
- `decltype` treats a pointer subscript as a value: `decltype(std::declval<T*>()[0])` yields `T`, where Clang and GCC yield `T&`. Use a subscript whose `operator[]` returns by value, or unary `+`, when the result feeds a dependent pattern.
- A `static_assert` inside a function template is not checked at instantiation; only namespace-scope assertions are evaluated.

`decltype` on an overload-set operand, bare function-name decay, non-dependent `enable_if` fallback, and `void_t` detection are covered and match Clang/GCC.

A `decltype` nested in a qualified partial-specialization pattern (for example `typename Box<decltype(T())>::type`) is a non-deduced context. The compiler binds parameters from the other arguments, then renders the operand as source, substitutes and resolves it for confirmation. Cast, ternary, shift, array-subscript and `declval` operands are supported; an operand that cannot be rendered is a hard error.

For nested-member checks (`T::type` and multi-level chains), the compiler uses the definition selected when the specialization was instantiated. Selection includes partial-specialization confirmation. A typedef declared by the primary is not a member of a partial specialization that omits it. Lookup fails when no selected definition provides the member.

`sizeof(expr)` type-checks its operand even though it is unevaluated: an invalid expression in a `decltype` trailing return type rejects the candidate, and an error from instantiating another template inside the operand stays hard. The parser reads a `sizeof` operand that starts with a template name as `sizeof(type)`; wrap such expressions in another pair of parentheses.

`static_assert` folds qualified static constexpr members and variable-template values such as `S::value` and `std::is_integral_v<int>` into the condition before judging it. The compiler rejects a false condition and rejects non-constant expression conditions (including runtime variables and non-constexpr calls) with an explicit diagnostic. Constant candidate expressions outside integral folding, such as member-pointer comparisons, keep their accepted behavior.

### 1. Language Semantics & Edge Cases
- **Copy Elision & Return Semantics**: Prvalue initialization is elided as guaranteed by C++17 (`T x = T(1);`). Returning local automatic variables by value applies C++11 implicit move semantics: overload resolution selects the move constructor before falling back to copy construction. Returning non-local or unmovable lvalues of move-only types (`std::unique_ptr`) is rejected at compile time.
- **Move Semantics & Value Categories**:
  - Expressions evaluate to lvalues, prvalues, or xvalues. Named variables and reference parameters evaluate as lvalues regardless of declared type (including `T&&`). Function calls returning rvalue references (`std::move(x)`) and explicit rvalue reference casts produce xvalues.
  - Lvalue references `T&` bind only to lvalues. Const lvalue references `const T&` accept both lvalues and rvalues, incurring a conversion penalty for rvalues during overload resolution. Rvalue references `T&&` bind exclusively to rvalues.
  - Overload resolution ranks exact value category matches over reference conversions: an rvalue argument prefers `T&&` over `const T&`.
  - Class definitions declaring user move constructors or move assignment operators suppress implicit copy operations. Copying a move-only type (such as `std::unique_ptr<T>`) across direct initialization, copy assignment, pass-by-value calls, or return statements triggers a compile diagnostic.
  - Forwarding references in function templates (`template <typename T> void f(T&& arg)`) deduce `T = U&` for an lvalue argument of type `U` and `T = U` for an rvalue. Calls returning lvalue references correctly deduce `T = U&`. Reference substitution collapses reference chains (`&` + `&&` -> `&`, `&&` + `&&` -> `&&`). Function template calls validate parameter compatibility of all arguments against instantiated signatures.
  - Standard headers `<utility>`, `<vector>`, and `<memory>` provide move-enabled resource management. Container buffer reallocation in `std::vector` moves existing elements into freshly allocated memory, `std::unique_ptr<T>` maintains single-owner semantics without copying, and `std::unique_ptr::reset` guards against self-reset.
- **Null Pointer Constants & Pointer Conversions**:
  - Integer literal zeroes (`0`, `0u`) and `nullptr` (`std::nullptr_t`, `decltype(nullptr)`) qualify as null pointer constants. Zero-valued variables, non-zero integers, and `false` are rejected.
  - Qualification conversions require every subsequent indirection level to be `const` when adding `const` to an intermediate level (`int**` converts to `const int* const*`, but not `const int**`).
  - Object pointers convert implicitly to `void*`; converting `void*` to a typed pointer requires `static_cast<T*>`.
- **String Literal Semantics**: String literals have type `const char[N]` with a null terminator (`sizeof("hello") == 6`). They decay to `const char*` for call arguments and pointer assignments, and cannot bind to `char*`.
- **Virtual Inheritance**: Virtual base specifiers are rejected with `virtual inheritance is not supported`. Single, multiple, and linear inheritance are supported. Consequently, converting a pointer to member of a virtual base to a pointer to member of a derived class is also unsupported (that conversion is ill-formed in C++17 anyway).
- **Pointers to Members & ABI**:
  - Data-member pointers (`T C::*`) evaluate to `i32` byte offsets within struct layouts. Null data-member pointers are encoded as `-1` (`0xFFFFFFFF`), distinguishing null from valid members at offset 0. The `.*` and `->*` operators produce an lvalue when the receiver is an lvalue.
  - Member-function pointers (`R (C::*)(Args...)`) pack `{ ptr: u32, adj: u32 }` into a WebAssembly `i64` value `(adj << 32) | ptr`. Bit 0 of `ptr` discriminates between non-virtual dispatch (bit 0 = 0, function table index `ptr >> 1`) and virtual dispatch (bit 0 = 1, vtable slot index `ptr >> 1`). The high 32 bits (`adj`) hold the signed `this` pointer adjustment for multiple inheritance subobject navigation. Null member-function pointers are encoded as `0i64`.
  - Base-to-derived conversions ([conv.mem]) implicitly convert `Base::*` to `Derived::*`. For data members, the conversion adds the subobject offset to non-null offsets. For member functions, the conversion adds the subobject offset shifted into `adj`.
  - Base-subobject byte offsets are target-specific: cppbolt uses the ILP32 Wasm model (4-byte pointers), so raw offsets printed by a program can differ from those of an LP64 native compiler. Dispatch results, not raw layout numbers, are the portable comparison.
  - Constructors and destructors of a class are responsible only for its direct non-virtual bases: construction in declaration order, destruction in reverse order. Indirect bases are initialized and destroyed once by their own class. Polymorphic classes reuse the vptr of their actual polymorphic base subobject; no phantom vptr is synthesized at offset zero.
  - A `using`/`typedef` name used as a base, mem-initializer, or allocated type resolves to the canonical class or specialization through one shared lookup, covering namespace-qualified, enclosing-class, nested, and multiple aliases to one specialization. Canonicalization applies to lookup and comparison keys only: diagnostics keep the source spelling, and distinct base subobjects keep distinct offsets under multiple inheritance. An initializer that names no base, member, or delegating constructor is diagnosed instead of silently default-constructing a base. Destructors for directly inherited specializations (explicit or synthesized) are registered and called through the same canonical identity.
  - A class with a final virtual destructor cannot be used as a base. Taking the address of a template-specialization member function forces its instantiation and resolves a real indirect-call index; unresolved targets are diagnosed rather than falling back to table index zero.
  - Applying `Base::*` to a derived receiver uses the same unambiguous, accessible-base rules as converting `Base::*` to `Derived::*`. A non-const member-function pointer cannot be applied to a const object. A `noexcept` member-function pointer converts to the potentially-throwing type; the reverse is rejected. Calls through a member-function pointer yield the declared return type, including floating-point, pointers, references, `void`, and structures.
  - A virtual function is identified by its name, adjusted parameter types (top-level cv dropped, arrays and functions decayed), cv and ref qualifiers; return type and `noexcept` are checked separately on override. Covariant pointer and reference returns are validated for accessibility and ambiguity, and the returned value is adjusted to the base interface's subobject at runtime. Overloaded virtuals get distinct vtable slots, and final overriders are resolved per slot. Template-specialization bases are instantiated before derived layout. Explicit destructor calls resolve through the shared destructor lookup. Binding a reference to a base subobject applies the same offset adjustment as taking its address. `override` implies `virtual`; a same-signature method overrides even without a keyword. Overriding a `final` method, marking a method `override` when nothing matches, and putting `override`/`final` on a static or non-virtual method are rejected. Class-level `final` is parsed and deriving from it is rejected. Virtual member-function templates are rejected.
- **Operator Overloading Boundaries**: User-defined operator overloads for arithmetic, relational, bitwise, assignment, subscript `[]`, smart-pointer `->`, dereference `*()`, functor `()`, postfix `++`/`--`, and conversion operators `operator T()` are supported. Method ref-qualifier overloading with const-lvalue references (`const &`) is explicitly rejected with `const overloading is not supported`.
- **Chained `operator->` & Cycle Detection**: In accordance with C++17, member access via `->` recursively resolves through chained `operator->()` overloads returning class objects or references until a raw struct pointer is reached. Cycle detection prevents compile-time recursion loops (`circular operator-> delegation on '<class>'`), and recursion depth is budgeted to 128 hops.
- **C++17 Lambda Expressions**: Lambdas desugar into anonymous closure structs (`__lambda_N`) holding captured state as either by-value copies or references. The synthesized `operator()` is `const`-qualified unless marked `mutable`, enforcing immutability on by-value captures. Return types can be explicitly annotated with trailing return syntax (`-> T`) or automatically deduced from `return` statements. Captureless lambdas (`[]`) synthesize a static `__invoke` trampoline enabling implicit conversion to standard C function pointers (`R (*)(P...)`), including as return statement targets and via unary `+` decay (`+[](){}`). Default captures (`=`, `&`) must strictly appear first in the capture list, and free-variable discovery traverses `RangeFor`, `StructuredBinding`, and nested `Lambda`/`New` constructs.
- **Comma Operator & Sequence Expressions**: The comma operator `(a, b)` evaluates operand `a` for side effects, discards its result, and yields the value and type of operand `b`. Comma expressions parse at precedence 1. Function call arguments, template arguments, and multi-declarator definitions parse at precedence 2, preventing unparenthesized commas from being treated as sequence operators.
- **C++17 Selection Initializers**: Selection statements support initialization clauses: `if (init; condition)` and `switch (init; condition)`. The initializer statement executes before the condition, and variables declared within it remain scoped to the selection construct and its branches. Deep `else if` chains flatten iteratively to prevent stack overflow during AST traversal.
- **Non-Static Data Member Initializers (NSDMI) & Aggregates**: Struct and class fields support in-class default member initializers (`int x = 10;`, `int y{20};`).
  - When user-defined constructors omit a field from their member initializer list, the compiler initializes that field with its default member initializer.
  - In accordance with C++17 [dcl.init.aggr], non-static data member initializers do not disqualify a class from being an aggregate. User-declared constructors disqualify a class from being an aggregate.
  - When an aggregate is initialized with fewer elements than fields, omitted trailing fields initialize from their default member initializers if present, or zero-initialize when omitted.
- **List Initialization & Aggregates**: Braced initializer lists (`{...}`) work across variable declarations, namespace-scope (global) variables, constructor member initializers (`: member{val}`), returns, call arguments, assignments, typed temporaries (`Type{args...}.member()`), and heap allocations (`new T{...}`, `new T[n]{...}`).
  - Direct-list initialization allows selecting `explicit` constructors; copy-list initialization rejects them. Empty braces (`{}`) value-initialize scalars and enums to zero, clear aggregate fields, or call default constructors.
  - Under C++17 aggregate rules, classes qualify as aggregates when they have no user-declared constructors, no private or protected non-static data members, no virtual functions, and no virtual or private base classes. Public non-virtual bases initialize as initial subobjects, either with nested braces (`Derived{{base_args}, derived_args}`) or flattened across the outer list.
  - Narrowing conversion checks follow C++17 [dcl.init.list] p7, rejecting conversions from floating-point to integer, `double` to `float` (unless an exact constant literal), and between integer types with sign changes or smaller ranges. Compile-time constant expressions, including negative integer literals, are accepted when the value fits the destination type.
  - Single-object `new T{...}` direct-initializes the heap object. Array `new T[n]{...}` initializes explicit elements and runs a WebAssembly loop to value-initialize omitted trailing elements up to `n`.
  - Initializer-list constructors taking `std::initializer_list<T>` receive a frame-backed pointer-and-size view. The backing array stays live through the full expression; elements of local initializer-list variables are destroyed at scope exit.
  - Multiple viable initializer-list constructors are ranked by element conversions: exact matches beat integral promotions, which beat other standard conversions. A narrowing candidate is discarded, and its diagnostic is reported only when no viable candidate remains. Empty braces use the initializer-list constructor when the class has no default constructor.
  - Nested brace lists such as `std::vector<std::vector<int>> v{{1, 2}, {3, 4}}` are resolved against the chosen element type after constructor selection.
  - Namespace-scope lists and braced containers are initialized before `main` runs. The backing array of a namespace-scope `std::initializer_list` is placed in `main`'s frame, which outlives every use of the list.
  - C++17 aggregate brace elision ([dcl.init.aggr] p11) allows flat initializer lists to initialize nested array and aggregate subobjects without intermediate braces (`struct S { int a[2]; int b; }; S x = {1, 2, 3};`). The compiler consumes elements from the outer list sequentially for subaggregate fields. Initializers exceeding declared aggregate capacity trigger a compile diagnostic (`tests/negative/aggregate_excess_elision.cpp`).
  - Standard array (`std::array`) uses upstream LLVM libc++ 23.1.5 aggregate layout (`_Tp __elems_[_Size]`) without constructor shims, preserving pure aggregate semantics for single-brace (`std::array<int, 3> a = {1, 2, 3};`) and double-brace initialization. Out-of-range indexing in `std::array::at()` terminates execution with a diagnostic via `std::__throw_out_of_range`.
- **Extended Casts (`reinterpret_cast`)**: Supports C++17 `reinterpret_cast<T>(expr)` between pointer types, pointer and integer types (matching the 32-bit ILP32 pointer width), and reference types (`reinterpret_cast<T&>(v)`). Does not invoke user-defined conversion operators or constructors. Scalar floating-point reinterpretations by value are rejected; bit patterns of floats can be inspected via pointer or reference reinterpretation (e.g. `*reinterpret_cast<uint32_t*>(&f)`).
- **Template Core**:
  - Class templates, function templates, alias templates, and member method templates support type, non-type, and variadic parameter packs (`template <typename... Args>`). C++11 variadic templates, template-template parameter packs (ADR 0013), and C++17 fold expressions (ADR 0014) are fully supported.
  - Instantiation follows a two-phase lookup model (ADR 0010, ADR 0012, ADR 0013, ADR 0014). The parser preserves template declarations in the AST (`TemplateDecl`), and semantic analysis resolves names and types during concrete specialization.
  - Parameter packs expand into concrete AST nodes during template substitution before code generation.
  - C++17 fold expressions ([expr.prim.fold]) expand parameter packs across all four fold shapes (unary left, unary right, binary left, binary right) for all 32 operators, including pointer-to-member operators `.*` and `->*` (ADR 0015). Folds expand during template substitution with standard associativity, apply empty pack fallbacks (`&&` yields `true`, `||` yields `false`, `,` yields `void()`), and evaluate in constexpr contexts, dependent array bounds, and non-type template arguments (`src/sema/fold_expansion.rs`).
  - Pack expansion syntax (`pattern...`) is supported across function call arguments, braced initializer lists, base class specifiers (`struct S : Bases...`), constructor member initializers (`: Bases(args)...`), template argument lists (`Tuple<Tail...>`), lambda captures (`[args...]`, `[&args...]`), and alignment specifiers (`alignas(Ts...)`). Base class pack expansion supports multiple inheritance: base subobjects are laid out sequentially with their respective offsets, methods and constructors dispatch to all base subobjects, and duplicate direct base classes are diagnosed as errors.
  - When multiple parameter packs appear in the same expansion pattern, they must have identical lengths; expanding packs of mismatched lengths is rejected with a compile error. Unexpanded parameter packs in expressions or types trigger explicit diagnostics.
  - The `sizeof...(pack)` operator evaluates at compile time to the number of elements in the parameter pack as a `size_t` constant expression. The `alignof(T)` operator evaluates the alignment requirement of a type at compile time.
  - Function template argument deduction deduces parameter packs from trailing arguments, including empty packs, forwarding reference packs (`Args&&...`) with reference collapsing (`&` + `&&` -> `&`, `&&` + `&&` -> `&&`), and structural pack deduction in template instance arguments (`f(Tuple<As...>, Tuple<Bs...>)`). A function parameter pack before the deduced pack is a non-deduced context: the trailing pack takes all remaining arguments and the leading pack stays empty (`tests/templates_operators/variadic_two_trailing_packs.cpp`).
  - Function template partial ordering ([temp.func.order]) compares synthesized parameter signatures using deduction from synthetic types per ISO C++11 [temp.func.order]: a non-pack parameter is strictly more specialized than a parameter pack, and more specialized function templates beat less specialized ones in overload resolution ([over.match.best]). Ambiguous partial ordering ties trigger a compile error.
  - Non-type template parameters evaluate compile-time constant expressions for integral and boolean types, including arithmetic, bitwise, comparison, logical, ternary, and `sizeof` expressions (`src/sema/constexpr_eval.rs`). Relational operators `<` and `>` inside template arguments are disambiguated from closing delimiters via parenthesized depth tracking. NTTP packs in partial specializations (`Sum<First, Rest...>`) bind and evaluate recursively.
  - Explicit (full) specialization (`template <> struct S<int> { ... };`) replaces the primary template when argument types match exactly.
  - Partial class template specialization (`template <typename T> struct S<T*> { ... };`) ranks candidate specializations using pattern matching and specificity scoring. Ambiguous specializations are rejected at compile time.
  - Alias templates (`template <typename T> using Alias = Target;`) substitute arguments and unpack dependent type aliases during instantiation.
  - Default template arguments populate omitted trailing type and non-type parameters for class and function templates.
  - Static members declared in base classes or typedef aliases propagate to derived template specializations while preserving original storage addresses.
  - Type resolution recursively unwraps pointers, references, const qualifiers, and arrays, generating concrete struct layouts before calculating member access offsets.
  - Non-template structs compute layouts after resolving template fields, giving fields valid offsets and sizes. Non-template functions accept and return template instance types.
  - Class template member methods instantiate lazily on first call, address-of reference, or operator overload lookup (`operator[]`, unary operators). Unused member methods are neither typechecked nor emitted into WebAssembly.
  - Non-virtual class template destructors instantiate eagerly alongside virtual methods so synthesized cleanup logic can drop values on scope exit. Dynamically instantiated template classes containing fields with non-trivial destructors synthesize cleanup methods and copy operations.
  - Function template overload resolution deduces type arguments from values, references, const references, top-level const pointers, and template instance arguments. When a function template parameter is not a reference type, array arguments undergo array-to-pointer decay per C++17 [temp.deduct.call] p2 (`int[N]` decays to `int*`). This allows templates such as `std::sort` to deduce pointer iterator types from raw arrays. When a parameter is a reference type (`T&`, `const T&`), the non-decayed array type is preserved. Candidate registration tracks overloads sharing identical parameter counts by signature. Explicit template arguments (`func<int>(val)`, `func<Inner<int>>(val)`) override deduction and parse nested template types. Default argument expressions fill omitted trailing parameters for both free and member template functions. Exact non-template function overloads take precedence over template specializations.
   - Substitution into a function template signature is the immediate context for C++17 SFINAE. An invalid type formed there (for example a negative dependent array bound, also via a defaulted non-type template parameter) removes only that candidate; the remaining candidates are still ranked. Errors from instantiating another template while resolving a signature type stay hard, as do errors in the body of the selected specialization. Member templates follow the same rule: their bodies are substituted only after a candidate is selected, so a rejected candidate registers no method or pending instantiation.
  - Out-of-class method definitions match class template and concrete struct declarations by parameter types and const qualification, including across multi-part namespace paths (`Outer::Inner::Class::Class()`).
  - Member template parameters shadow outer class template parameters with identical names during class instantiation.
  - Expression calls on struct instances dispatch to `operator()` only when an explicit call operator or member template `operator()` exists.
  - Nested class declarations inside class templates clone and specialize on outer template instantiation, generating qualified types (such as `Container<int>::Node`), computing distinct field layouts, and registering member methods.
  - Nested class type specifiers (`Outer::Inner`) enforce access control during type resolution. Private nested types can only be referenced from within the enclosing class, its member methods, or template specializations parameterized with the nested type. Referencing private nested types externally triggers a compile diagnostic (`tests/negative/nested_type_private_access.cpp`). Nested class short names remain scoped to the outer struct and do not pollute the global namespace (`tests/negative/nested_class_unqualified_leak.cpp`).
  - Chained dependent type aliases resolve iteratively to a fixed point during template specialization, supporting arbitrary alias chains without fixed loop bounds (`tests/templates_operators/template_nested_alias_chain.cpp`). Member type aliases in the `std` namespace are restricted to templates actually defined within `std`.
  - Dependent member type specifiers require the `typename` prefix (`typename Container<T>::iterator`). Unqualified `typename` or non-type usage is rejected at parse time.
  - Instantiation recursion is limited to 500 levels (`template instantiation depth exceeded (limit: 500)`). The depth counter and instantiation stack are restored on every exit path, including errors.
  - Instantiation caches record only completed specializations. A specialization still being built stays on the instantiation stack for recursive references. A failed instantiation restores the layouts, aliases, globals, methods and synthesized declarations it wrote, letting a later request retry it. Function templates drop their in-progress marker when body analysis fails; a failed body is never reused as a successful specialization.

  - `decltype(expr)` is supported. The operand is resolved after template substitution; a parenthesized lvalue gives `T&` and an unparenthesized id-expression or member access gives the declared type. Trailing return types (`auto f(T x) -> decltype(x.member())`) take part in template signature substitution, so an invalid expression discards only that candidate. See `tests/templates_operators/decltype_value_categories.cpp` and `tests/templates_operators/decltype_sfinae_fallback.cpp`.
- **Exception Handling Semantics & Unwinding**:
  - `try`, `catch`, and `throw` compile directly to WebAssembly Phase 4 exception instructions (`try_table`, `throw`, `throw_ref`).
  - Functions containing calls, throws, or try blocks allocate a 64-bit runtime liveness mask (`cleanup_mask_local: i64`) to track object construction. Single functions are limited to 64 tracked RAII cleanup objects. Functions exceeding this ceiling fail compilation.
  - When an exception propagates, active automatic variables, subobjects, and completed expression temporaries are destroyed in strict reverse order of construction.
  - Destructor invocations during stack unwinding are wrapped in `try_table (catch_all -> unreachable)` blocks to immediately invoke `std::terminate()` if a destructor throws during unwinding.
  - Multiple `catch` clauses per `try` statement are supported. Per ISO C++17 [except.handle], `catch (...)` must appear as the final clause in any try block.
  - Typed exception objects are allocated on the heap with a 16-byte header recording type ID, destructor vtable index, flags, and size. WebAssembly tag 0 carries the pointer to this header.
  - Dynamic catch matching via `__cppbolt_can_catch` supports exact types, pointer conversions (`char*` to `const char*`, object pointers to `void*` or `const void*`), and derived-to-base class conversions for single and multiple inheritance, applying subobject byte offsets.
  - Catching by reference (`catch (T&)` or `catch (const T&)`) binds directly to the adjusted subobject without copying, supporting in-place mutation. Catching by value (`catch (T)`) invokes copy construction or byte copy, destroying the local copy at catch scope exit.
  - The exception object destructor is called and its heap allocation is freed when handling completes normally or exits via return. Rethrow (`throw;`) preserves the original exception object.
  - In conditional expressions (`?:`, `&&`, `||`), temporaries in unexecuted branches are not constructed; normal and unwinding cleanups check the liveness mask and non-null slots to prevent double destruction.
  - Reference binding to conditional expressions (`const T& ref = cond ? T(1) : T(2)`) extends the lifetime of the dynamically constructed temporary until the enclosing lexical scope exits.
  - Semantic analysis rejects throwing `void`, incomplete types, or abstract classes, and rejects catching abstract classes by value or declaring rvalue-reference catch handlers (`catch (T&&)`).

### 2. Nesting Limits per Construct

To protect WebAssembly engine shadow stacks from exhaustion when compiling deep programs in Web Workers, the compiler enforces per-construct nesting budgets (`src/depth.rs`). One construct cannot exhaust the budget of another:

| Construct | Limit | Deepest Accepted Input (Native & Wasm) |
|---|---|---|
| **Expressions** | 4,000 | Parenthesized conditional costs 2 levels |
| **Parentheses** | 1,600 | 1,600 nested parentheses |
| **Call Argument Lists** | 1,500 | 1,500 nested calls |
| **Statements** | 1,600 | 1,599 nested `if` statements |
| **Compound Blocks** | 1,600 | 1,599 nested `{}` blocks |
| **Declarations** | 1,600 | 1,600 nested declarations |
| **Type Expressions** | 1,600 | 1,600 nested type qualifiers |
| **Preprocessor Conditions** | 1,600 | 1,600 nested `#if` conditions |
| **Include Depth** | 128 | 128 nested `#include` directives (129 is rejected) |

These limits are verified by `tests/nesting.rs` and `tests/wasm_stack_safety.rs`.

Wide left-associative expressions (sums of 20,000 terms), string concatenations (4,000 terms), and `else-if` chains (5,000 branches) are flattened iteratively and do not consume recursion depth. A step in an overloaded chain that needs a user-defined conversion recompiles its prefix as a call argument, so those chains consume expression depth. The compiler rejects them past 4,000 levels.

### 3. Printf Runtime Specifications
The embedded `printf` engine (`src/runtime/format.rs`) supports:
- Specifiers: `%d`, `%i`, `%u`, `%o`, `%x`, `%X`, `%c`, `%s`, `%e`, `%E`, `%f`, `%g`, `%G`.
- Modifiers: `h`, `hh`, `l`, `ll`, and `z`.
- Flags: `0` (zero-pad), `-` (left-align), `+` (sign), ` ` (space sign), `#` (alternate form).
- Dynamic precision: `.*` is supported. (Dynamic width `*` is not implemented).
- Unsupported conversions: `%p` and `%n`.
- NaN and Infinities: Zero padding falls back to spaces; sign of NaN is implementation-defined.
